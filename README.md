# 市政招标公告完整性核对工具

面向招标公告采集员的网页工具：在现有 FastAPI 应用中新增“完整性核对”页，
通过**两次分页遍历 + 详情核对**发现翻页期间站点更新导致的漏采，并只把
核对通过的完整清单原子保存到 SQLite。

## 解决的问题

分页目录在采集过程中可能更新（新公告插入、公告撤下、顺序变化），单次遍历
无法发现自己漏采或错采。本工具的核对流程：

1. **第一轮目录遍历**：从输入的目录 URL 沿“下一页”逐页读取公告编号、详情
   链接和出现顺序。
2. **抓取全部详情**：逐条打开详情页，读出详情页上的公告编号。
3. **第二轮目录遍历**：重新从入口走一遍全部分页。
4. 只有同时满足以下条件才判定本轮**完整**并保存：
   - 两轮各页的公告编号**及顺序**完全一致；
   - 列表编号与详情页编号逐条一致；
   - 没有跨页（或同页）重复编号；
   - 没有任何抓取或解析失败。
5. 不完整时把异常来源（目录页/详情页 URL、编号、页码、原因）列为
   **待复查**，本轮不写入完整清单；**上次完整清单原样保留**，并在页面上
   明确标注“不是本轮结果”。

## 快速开始（Docker Compose，启动后可完全离线使用）

```bash
docker compose up --build
# 浏览器打开
#   http://localhost:8000/            完整性核对页
#   http://localhost:8000/demo/       本地示例站（场景控制）
```

镜像构建时安装依赖；运行时只服务本机生成的页面，网页不引用任何外部字体、
脚本或样式，断网后仍可完整浏览和操作。SQLite 数据库在宿主机 `./data`
目录中持久化。

无 Docker 时的本地运行：

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
# 数据库位置可用环境变量覆盖：INTEGRITY_DB_PATH=/path/to/integrity.db
```

## 本地示例站（可复现目录变动）

`/demo/` 是随应用一起运行的离线招标公告站点，3 页、每页 5 条。场景通过
服务端状态切换，核对入口始终是同一个固定 URL
（`http://localhost:8000/demo/catalog`），便于反复复现：

| 场景 | 行为 | 预期核对结果 |
| --- | --- | --- |
| 稳定目录 | 两轮遍历完全一致 | 完整，保存新快照 |
| 翻页期间更新 | 第一轮 3 次目录请求后，目录头部插入 1 条新公告 | 两次目录不一致，待复查 |
| 跨页重复编号 | 同一编号出现在第 1、2 页 | 跨页编号重复，待复查 |
| 详情编号错配 | 列表编号与详情页编号不同 | 详情错配，待复查 |
| 详情读取失败 | 某条详情返回 404 | 抓取失败，待复查 |

推荐演示顺序：先跑“稳定目录”得到一份完整清单，再切换到任意异常场景，
结果页会保留旧清单并标注“注意：以下为上次完整清单，不是本轮结果”。
“翻页期间更新”场景按目录请求计数切换代次，每次切换场景都会自动重置计数；
手动预览目录后可在示例站首页点击“重置计数”。

## 页面与接口

- `GET /`：完整性核对页，输入目录 URL 发起核对。
- `POST /check`：表单提交，核对完成后 303 跳转到结果页 `/runs/{id}`。
- `GET /runs/{id}`：结果页，含运行信息、异常来源表（全部标为待复查）、
  本轮完整清单或上次完整清单（含明确归属说明）、本轮读取条目及详情核对状态。
- `GET /demo/`：示例站场景控制；`GET /demo/catalog`、
  `GET /demo/notice/{id}` 为示例目录与详情。
- JSON API（便于脚本调用）：
  - `POST /api/check`，请求体 `{"catalog_url": "..."}`；
  - `GET /api/runs/{id}`：某轮完整记录（含异常、条目、快照）；
  - `GET /api/snapshots/latest?catalog_url=...`：该目录最近一次完整清单；
  - `GET /api/snapshots/{id}`：按 id 取完整清单；
  - `GET /healthz`：健康检查。

## SQLite 数据模型

数据库默认在 `data/integrity.db`（可用 `INTEGRITY_DB_PATH` 覆盖）。

- `runs`：每轮核对的状态（`complete` / `flagged` / `failed`）、两轮页数与
  条数、关联快照、待复查标记。
- `run_pages`：每一轮每一页的 URL 与该页编号顺序（JSON），用于事后比对。
- `items`：本轮读取到的条目、来源目录页 URL、详情 URL、详情核对状态。
- `anomalies`：异常来源与原因，`is_reviewed=0` 表示待复查。
- `snapshots` / `snapshot_items`：**仅**核对通过时写入的完整清单及每条的
  来源 URL。

一次核对的所有写入在单个 `BEGIN IMMEDIATE` 事务中完成：要么整轮可见，
要么全部回滚（见 `tests/test_db.py::test_persist_is_atomic_when_write_fails`）。
失败轮次不会创建快照，因此上次完整清单不会被覆盖。

## 解析约定

- 公告编号识别：元素 `data-*-id` 属性优先，其次“项目编号/招标编号/公告编号
  …：xxx”标签文本、`【编号】` 形式。
- 分页识别：`rel="next"`、“下一页”文本、分页容器中的数字页码，以及
  `page/pageNo/p` 等查询参数递增。
- 详情链接：取条目容器内非分页锚点中最像标题/详情的链接。
- 安全上限：单次核对最多遍历 200 个目录页，超出即记异常并停止，避免死循环。

## 测试

```bash
pip install -r requirements-dev.txt
pytest -q
```

测试覆盖：解析器在表格/列表两种布局下的编号与顺序、分页识别、两轮比对、
重复编号检测、SQLite 原子写与快照保留，以及对真实本地 uvicorn 服务的
端到端核对（包含全部五个示例场景、表单跳转和离线自包含页面检查）。

```
tests/         pytest 单元与端到端测试
Dockerfile / docker-compose.yml
```
